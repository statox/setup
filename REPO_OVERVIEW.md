## Functional

### Introduction

This repo is a personal collection of [Ansible](https://docs.ansible.com/) playbooks and roles that Adrien Fabre ("statox") uses to provision his own machines: two personal/work Linux workstations, a Raspberry Pi, and a home server ("panda") that hosts a stack of self-hosted services.

- **Context**: personal project, single author, not published as a reusable tool for others.
- **Activity**: actively maintained. 254 commits since the first commit on 2022-01-31, with the most recent commit 3 days before this report. Development is bursty and self-directed, not scheduled.
- **People involved**: one contributor (`git shortlog` returns no author breakdown because the repo has a single committer identity throughout).
- **Maturity**: mature and working for its owner, but explicitly not polished. The [`README.md`](README.md) states "It is useful only to me, don't expect the cleanest code," and lists 14 known-broken or unfinished items in its own TODO section.

## Code

### Architecture

#### Directories map

```
setup/
├── install_*.yml        top-level playbooks, one per machine (adrien-XPS-9320, afabre-PF514G4Z, panda, raspberry)
├── run, run-role         wrapper scripts around `uv run ansible-playbook` / ad-hoc role runs
├── bootstrap              installs uv, copies inventory.sample -> inventory, installs galaxy collections
├── ansible.cfg            points ansible at the local `inventory` file
├── inventory(.sample)     defines hosts: local, raspberry, panda, temp_ec2
├── vars/                  config.local (gitignored, per-machine) + secrets.yml.enc (ansible-vault)
├── pyproject.toml, uv.lock  Python/uv-managed dependency pin for ansible + ansible-lint
└── roles/
    ├── system/    root-level OS config shared by workstations + panda (docker, firewall, i3, sudo...)
    ├── user/      non-root workstation setup (dotfiles, shell, editor, dev toolchains)
    ├── work/      work-machine-only add-ons (1Password, VPN, corporate GitLab, cloud CLIs)
    ├── ui/        desktop appearance (nerdfonts)
    ├── server/    dockerized services deployed on panda, behind Traefik
    ├── raspberry/ Pi-specific roles (base, pihole, portainer)
    └── dev/       empty directory, no content
```

#### Modules interactions

A playbook (`install_<host>.yml`) is a flat list of roles applied in order, each optionally `become: true` for root-level steps. There is no shared "framework" module - reuse happens at the role level:

- `roles/server/docker_compose_setup` is a shared helper role. Every app role under `roles/server` (`traefik`, `gitea`, `immich`, `servarr`, etc.) `import_tasks`s it instead of duplicating docker-compose deployment logic: copy `files/docker/` to `~/.docker-apps/<app>`, template `.j2` files with vars, then `docker compose up`.
- Ordering dependencies between roles are expressed only as comments in the playbooks, not enforced in code - e.g. `ui/nerdfonts # Must happen before user/dconf` and `user/github # Must happen before dotfiles` in [`install_adrien-XPS-9320.yml`](install_adrien-XPS-9320.yml).
- On `panda`, `install_panda.yml` opens firewall ports centrally before any service role runs, then deploys `traefik` (ingress) and `portainer` (management UI) before the actual apps.

```
install_panda.yml
  -> system/base, system/sudo, system/docker   (root-level prerequisites)
  -> server/firewall                            (open only required ports)
  -> server/traefik                             (reverse proxy / ingress)
  -> server/portainer                           (docker management UI)
  -> server/{transmission,elk,api-db,gitea,planka,servarr,immich}
       each: import_tasks server/docker_compose_setup
```

#### Environment integration

This is not a library or a service with external consumers - it is infrastructure-as-code the owner runs against their own machines. The "consumers" are the four target hosts declared in [`inventory`](inventory): `local` (the current workstation), `raspberry`, `panda`, and `temp_ec2`. The `panda` host is itself the deployment target for a further layer of self-hosted web services (Gitea, Immich, etc.), each exposed publicly through Traefik under `*.statox.fr` subdomains, with TLS actually terminated by Cloudflare in front of Traefik.

### Data Model

This repo has no application data model of its own - it provisions infrastructure. The closest things to "data" are:

- **Ansible variables**: machine-local, non-secret settings in `vars/config.local` (git-ignored, created from [`vars/config.local.sample`](vars/config.local.sample)) - GPG identity, git identity, scanner host.
- **Secrets**: encrypted at rest in [`vars/secrets.yml.enc`](vars/secrets.yml.enc) via `ansible-vault`, decrypted at playbook run time and injected into roles as normal Ansible variables (e.g. `transmission_user`).
- **Deployed services' own data**: each `roles/server/*` app manages its own persisted data inside its docker containers/volumes (Postgres for Gitea/Immich/Planka, Elasticsearch for the ELK stack, SQLite-backed apps for the servarr suite). This repo only deploys those services - it does not define their internal schemas.

### Patterns

- **Shared deploy helper for docker apps**: every `roles/server/*` app role follows the same shape - `tasks/main.yml` with variable guards (`fail` if a required var is missing), then `import_tasks: ../../docker_compose_setup/main.yml`, backed by `files/docker/docker-compose.yml` + `files/docker/.env.j2`. This is the most consistent pattern in the repo.
- **Idempotency via guard checks**: root-level system/user roles use `stat`/`lineinfile`/`ini_file`/`creates:` checks before installing apt keys, repos, or running install scripts, rather than relying solely on module state.
- **Manual-step reminders**: roles that need a step Ansible can't automate use `ansible.builtin.debug` "[IMPORTANT]" messages or `ansible.builtin.pause` (e.g. `work/sdm` reminding to run `sudo sdm install`, `user/github` pausing for a manual SSH-key upload to GitHub).
- **Ordering by comment, not code**: cross-role dependencies are documented as inline comments in the top-level playbooks instead of Ansible `meta/main.yml` dependencies or handlers.
- **Inconsistency - duplicated apt-repo bootstrap**: the GPG-key/apt-repo install idiom is repeated near-identically across `user/github`, `user/dev`, `user/kubectl`, `work/1password`, `work/cloudflare-warp`, and `work/vault`, instead of being factored into one shared task file.
- **Inconsistency - duplicated firewall logic**: `roles/system/firewall` and `roles/server/firewall` are near-duplicates, each carrying a `# TODO Merge with roles/<other>/firewall` comment pointing at the other.
- **Dead/orphaned roles left in place**: several roles exist but are not referenced by any active playbook line - `roles/system/steam`, `roles/dev` (empty directory), and (in `install_adrien-XPS-9320.yml`) `work/base`, `work/gitlab`, `work/vault`, `work/sdm`, `raspberry/portainer` are all commented out rather than removed.

### Setup

Setup is documented in the [`README.md`](README.md) "How to use this repo" section:

1. `sudo ./bootstrap` - installs `uv` and the Ansible Galaxy collections.
2. Update the `inventory` file (created from [`inventory.sample`](inventory.sample) by `bootstrap`) if needed.
3. Update `vars/config.local` (created from [`vars/config.local.sample`](vars/config.local.sample) manually - `bootstrap` does not do this step).
4. Create `install_$(hostname).yml` for a new machine, following an existing playbook as a template.
5. Run `./run install_<host>.yml -C` for a dry run, then `./run install_<host>.yml` to apply.

For playbooks needing secrets, `README.md` documents the ansible-vault flow using [`vars/get-vault-password.sh`](vars/get-vault-password.sh), which shells out to `dcli` (Dashlane CLI) to fetch the vault password from a Dashlane secure note.

Not applicable in the traditional sense - this repo has no compiled artifact. "Building" is running the playbooks, which is covered in Setup above. ## Repo High Level Analysis

### Quality & Improvement Areas

- **Consistency where it counts most**: the `roles/server` area's shared `docker_compose_setup` pattern is the strongest piece of design in the repo - every dockerized app follows the same guard-then-deploy shape, so adding a new self-hosted service is low-effort and predictable.
- **Duplicated bootstrap logic elsewhere**: outside `roles/server`, the same apt-key/apt-repo installation idiom is copy-pasted across `roles/user/github`, `roles/user/dev`, `roles/user/kubectl`, `roles/work/1password`, `roles/work/cloudflare-warp`, and `roles/work/vault` instead of being factored into a shared task file. This is exactly the kind of duplication `docker_compose_setup` avoided elsewhere in the repo - worth extracting into one shared role or `include_tasks` file if these roles keep growing.
- **Firewall logic is split in two**: `roles/system/firewall` and `roles/server/firewall` are near-duplicates, each with a `# TODO Merge` comment pointing at the other. This has been known and unaddressed since at least the current commit history covers.
- **Accumulated dead code**: `roles/system/steam`, `roles/dev` (empty), and several `roles/work/*` subroles are left in the tree but commented out of every playbook rather than removed. This makes it harder for the owner (or a reader) to tell active roles from abandoned experiments at a glance.
- **No safety net beyond linting**: there is no CI and no automated test suite - reasonable for a single-owner infrastructure repo, but it means correctness depends entirely on manual dry-runs (`-C`) and `ansible-lint`, and mistakes surface only when a playbook is actually run against a real machine.
- **Self-aware about its own gaps**: the README's own TODO list (14 items) and numerous inline `# TODO` comments mean most known rough edges are already documented, which is a genuinely good practice for a repo without issue tracking.

### Ongoing Work

- **`servarr-stack` branch**: a git branch named `servarr-stack` exists alongside `master`, 7 commits ahead. Given the recent commit history on `master` already includes extensive `servarr:` work (Bazarr, Byparr, transmission creds, firewall wiring), this branch may be an earlier stage of the same effort that has since partly landed on `master`, or ongoing follow-up work not yet merged - worth the owner checking whether it's still needed or can be deleted.
- **i3 → sway migration**: `roles/system/swaywm` exists as an explicitly-marked WIP alternative to the long-established `roles/system/i3`, suggesting an in-progress but stalled window-manager migration. Neither playbook currently uses `swaywm`.
- No other multi-step migration or framework upgrade is evident from TODOs, branch names, or coexisting old/new implementations beyond the two items above.
